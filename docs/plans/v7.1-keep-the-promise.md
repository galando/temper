# v7.1 — Keep the Promise

**Proposed release:** v7.1.0
**Current version:** v7.0.1
**Theme:** Don't chase superpowers feature-for-feature. Temper has exactly one wedge no
competitor can copy in prompt-space: *the process is impossible to skip, and there's
evidence it ran.* This release does three things only — fix the two places where that
promise is currently false, remove the one adoption gap that loses users in the first
five minutes, and publish numbers instead of claims.
**Status:** Planning (detailed) · **Date:** 2026-07-22
**Supersedes:** the 8-workstream "close every gap" draft. Five of its eight workstreams
are cut or deferred below, with reasons — deletion is the point of this document.

---

## Thesis

Superpowers' moat is a network effect (~259k stars, 10+ harnesses, 14 à-la-carte
skills). No roadmap closes a network effect, and every workstream spent imitating its
surface area is a workstream spent fighting on its turf with less distribution.

Temper's moat is the deterministic spine. The winning position is narrow and honest:

> Superpowers tells the model to follow the process. Temper makes the process
> impossible to skip — and can prove it, in CI, with numbers.

Everything in this release either (a) makes that sentence *true* where it currently
isn't, or (b) makes it *visible* to someone who has never heard of temper. Anything
that does neither is out.

**Effort honesty up front:** Items 1 and 2 are genuinely small (days). Item 3 is not —
a benchmark credible enough to publish is the largest lift in this release and the only
durable differentiator in it. The plan is small in *scope*, not small in *effort*; the
effort is concentrated where it compounds.

## Item 1 — Integrity fixes: make the headline claims true

*Size: S (1–2 days). Zero new concepts — every change reuses existing gate/hook
machinery. Do first: item 3 publishes a benchmark of this system, and benchmarking a
system whose own gates don't meet its bar is marketing, not evidence.*

### 1.1 Give `temper gate design` real requirements

**Today:** `scripts/temper:807` — `design) reqs_json='[]'; all_pass=1` — an
unconditional PASS, which directly violates "no verdict without evidence."

**Change:** add `gate_design()` alongside `gate_plan()` (`scripts/temper:578`),
following the exact same conventions: `_req "name" 0/1 "detail"` rows, complexity read
via `cmd_state_get complexity`, awk/grep section checks, `reqs_json all_pass` output.

Requirements, mirroring `gate_plan()`'s complexity-conditional shape (design is only
mandatory for medium/complex — same rule the pipeline already uses):

| Req | Check (mechanical) | When |
|---|---|---|
| design not required | complexity is trivial/simple → single PASS row `"design optional for {complexity} complexity"` | trivial/simple |
| artifact exists | `{spec_path}/design.md` present (the artifact `agents/design.md` step 3 already produces) | medium/complex |
| alternatives considered | a `^#+ .*[Aa]lternatives` section exists and contains ≥2 entries (`^### ` subsections or `^- ` bullets within the section) | medium/complex |
| risks documented | a `^#+ .*[Rr]isks` section exists with ≥1 bullet | medium/complex |
| risks carry mitigations | every bullet in the Risks section contains `Mitigation:` (grep-checkable traceability; cheaper and less gameable than cross-file ID matching) | medium/complex |

**Co-evolve the prompt with the gate** (a gate the template can't satisfy is a bug
factory): `reference/design.md` and `agents/design.md` must specify the exact section
headings and the `Mitigation:` bullet format the gate greps for, and `agents/design.md`
gets the same "Deterministic Gate" step (`temper evidence add` + `temper gate design
--spec-path ...`) that `agents/{plan,build,review,check,eval}.md` already carry.

**Tests** (in `scripts/tests/test-temper.sh`, no model calls — same pattern as the
existing gate unit tests):
- trivial complexity + no design.md → PASS (design optional).
- medium complexity + no design.md → FAIL.
- medium + design.md with 1 alternative → FAIL; with 2 → next check.
- risks section missing / bullet without `Mitigation:` → FAIL; well-formed → PASS.
- `temper gate commit` aggregation: a red design gate blocks a real `git commit` in the
  scratch-repo hook test (extend the existing live pre-commit test).

**Not doing:** a live model fixture for design. The wiring-smoke feature is trivial
complexity, so `/temper:design` never fires there; a medium-complexity wiring fixture
is a follow-up if the unit tests prove insufficient — noted in `evals/README.md`'s
"Known limitations" per its own disclosure rule.

### 1.2 `/temper:init` installs the commit hook instead of recommending it

**Today:** `commands/init.md` step 4 only *recommends* `bash
$CLAUDE_PLUGIN_ROOT/scripts/hooks/install.sh`. Until the user runs it, raw `git commit`
is ungated and the flagship guarantee doesn't exist. The installer itself is already
safe to automate: marker-based clobber protection, refuses to overwrite a foreign
pre-commit hook, and a degradation contract (missing scripts → no-op hook).

**Change:** `commands/init.md` step 4 becomes: run the installer. Print what was
installed and the one-line opt-out (`rm .git/hooks/pre-commit` or skip via
`TEMPER_INIT_NO_HOOK=1`). Two behaviors preserved verbatim: a foreign pre-commit hook
is never clobbered (report it and print the manual instruction instead — the
installer's existing marker check already decides this), and re-running init stays
idempotent (installer already overwrites only temper-managed hooks in place).

**Tests:** extend the scratch-repo test in `scripts/tests/test-temper.sh`: init on a
clean repo installs the hook; init with a pre-existing foreign hook leaves it
untouched; init twice is a no-op the second time.

### 1.3 Config parser fails loudly instead of silently misreading

**Today:** `_cfg_get` (`scripts/temper:154–214`) parses a deliberate YAML subset but
ends in `2>/dev/null || echo "$default"` — any config it can't parse silently becomes
defaults. A user who writes a block-style list (`- item`, unsupported by design) gets
their config ignored with no signal.

**Change (refuse-loudly, not a rewrite):** add `temper config lint` — reuses the same
parser, but instead of swallowing errors it reports: unparseable lines, block-style
lists (detected via `^\s*- ` — the one known footgun the subset excludes by design),
and unknown top-level keys (vs. an allowlist of the keys `scripts/temper` actually
reads). `cmd_init()` and `/temper:init` run it automatically and print findings.
`_cfg_get`'s hot path stays exactly as-is — lint is a separate, explicit pass, so no
per-call overhead and no behavior change for valid configs.

**Tests:** lint flags a block-style list, an unknown key, a tab-indented line; clean
config → silent exit 0.

### Item 1 acceptance

- [ ] `temper gate design` returns FAIL for a medium-complexity spec with no design.md
      — and that FAIL blocks a real `git commit` via the existing hook, proven in
      `scripts/tests/test-temper.sh`.
- [ ] Fresh `/temper:init` on a clean repo leaves a working pre-commit hook behind with
      no extra user action; foreign hooks survive untouched.
- [ ] `temper config lint` exists, runs during init, and flags the three known
      misread classes.
- [ ] `CLAUDE.md` / `README.md` no longer contain any claim item 1 made true only now
      (audit the "physically blocks" language against post-fix reality).

## Item 2 — Auto-engagement lite: stop losing users in the first five minutes

*Size: S (~1 day). The one real adoption gap: superpowers engages on any task; temper
waits to be summoned. Close it with two cheap, deterministic-where-possible layers.*

### 2.1 `skills/using-temper` meta-skill

A new skill registered in `.claude-plugin/plugin.json` (7th entry), whose
*description* is the product — it must auto-trigger on feature/bug/refactor-shaped
requests: "add", "implement", "build", "fix", "refactor", "bug", "broken", "feature".
Body is short (≤60 lines, in keeping with the diet): route to `/temper` (full
pipeline) vs. `/temper:fix` (bug-shaped) vs. stay out of the way (questions,
explanations, one-line config tweaks), plus superpowers-style rationalization
counters, adapted to temper's actual value:

- "this is just a small change" → small changes are exactly what blast radius is for.
- "I'll add tests after" → the build gate mechanically requires RED before GREEN;
  after-the-fact tests can't produce a RED entry.
- "I already know the fix" → then evidence costs one command and proves it.

**Scope guard:** the skill only *routes into* the pipeline in projects where
`.claude/temper.config` or `.temper/` exists. In un-initialized projects it may
*mention* `/temper:init` once, never loop on it.

### 2.2 `UserPromptSubmit` nudge hook — deterministic detection

New `scripts/hooks/suggest-temper.sh`, wired into
`packs/hooks/settings.hooks.json` under `UserPromptSubmit` (the settings comment
already lists it as a supported event). Logic, all mechanical:

1. Exit 0 silently unless the project is temper-initialized (`.temper/` exists) —
   the false-positive control that makes this safe to ship on by default.
2. Exit 0 silently if a pipeline is already active (`.temper/state.json` present) or
   the prompt already starts with `/`.
3. Pattern-match the prompt against a small fixed regex set (feature/fix verbs +
   an object); on match, emit one line of `additionalContext`: *"This looks like a
   feature/fix request — `/temper` runs it through the gated pipeline."*
4. Config: `engagement.suggest` (default `true`) read via the existing `_cfg_get`
   path; `false` disables the hook output entirely.

Same degradation contract as every other temper hook: script missing or erroring →
exit 0, never block a prompt.

**Tests:** pure stdin/stdout — feed crafted `UserPromptSubmit` JSON payloads in
`scripts/tests/test-temper.sh` and assert output/silence for: feature-shaped prompt in
initialized repo (suggests), same prompt with active state (silent), question-shaped
prompt (silent), uninitialized repo (silent), `engagement.suggest: false` (silent).
No model calls anywhere.

### Explicitly deferred: the PreToolUse edit-blocker

The original draft's third layer — block/suggest on Edit/Write with no active build
state — is the most novel idea and the most likely to infuriate users on false
positives (hotfixes, docs edits, config tweaks). Ship the two soft layers, watch, then
decide; the hook plumbing above makes it a config flag later (`engagement.enforce:
suggest|block|off`), reserved now, unimplemented.

### Item 2 acceptance

- [ ] In an initialized project, a prompt like "add rate limiting to the reset
      endpoint" (no slash command) produces the one-line nudge; the same prompt
      mid-pipeline produces nothing.
- [ ] All five hook test cases pass without a model call.
- [ ] `using-temper` triggers on feature-shaped requests in live smoke use, and does
      not fire on "explain how X works".
- [ ] Combined added prompt weight ≤ ~80 lines (skill + nudge text) — engagement must
      not undo the diet.

## Item 3 — The receipts: a published temper vs. bare-Claude benchmark

*Size: L — the largest lift in the release, on purpose. Temper already owns the only
self-eval harness in this space (`evals/`: three-tier verification, anchor+signal
keyword matching, a live-verified v6-vs-v7 baseline). This item grows it from a
regression harness into a published, reproducible benchmark.*

**Deliberately two conditions, not three.** (a) bare Claude Code, (b) temper, same
model, same fixtures. Running superpowers as condition (c) is deferred: benchmarking a
competitor "fairly" is a methodology minefield (version drift, prompt-tuning
accusations) that turns a data release into a flame war. Bare Claude Code *is* the
exhortation-only condition — it's what proves "gates catch what narration misses."
Add (c) later only if the two-way table lands and someone external asks.

### 3a — Harness extensions (`evals/run-fixture.sh`, new `evals/run-benchmark.sh`)

*Size: M.*

1. **Bare condition.** `TEMPER_EVAL_CONDITION=bare` runs `claude -p` with **no**
   `--plugin-dir` and a standardized neutral prompt per stage, fixed in the harness
   (not per-fixture, to prevent tuning): review → *"Review this codebase and report
   any defects you find."*; check → *"Verify that the tests cover the requirements
   documented in intent.md; report any gaps."* Scoring for bare runs is
   transcript-only by construction (no CLI, so evidence tiers are unreachable) —
   that asymmetry is not a flaw, it is the finding. Every result reports its tier.
2. **Catch criteria per condition.** temper: tier 1 (`gate-blocking-evidence`) only —
   the existing strict bar. bare: anchor+signal match against the transcript (the
   existing tier-3 machinery, reused verbatim). Both published side by side, tier
   labeled, so the table itself shows "found and narrated" vs. "found and mechanically
   blocked."
3. **False-positive scoring on clean fixtures.** New fixture flavor:
   `expect.json` gains `"seeded": false`. For temper, an FP is mechanical: any
   evidence entry at blocking severity / any failing `--scenario` row on a clean
   fixture. For bare, keyword matching can't work (there's no anchor to name) — an
   LM-judge answers one narrow yes/no question: *"Does this transcript assert that a
   concrete defect exists (not a style suggestion or a hypothetical)?"* Judge prompt
   ships in the repo (`evals/judge/fp-judge.md`, building on the existing `eval-judge`
   skill), and every judged transcript is retained in the results artifact so any FP
   verdict can be re-derived. This is the one non-mechanical link in the chain —
   disclosed as such in the methodology section.
4. **Repetition.** `N=5` runs per fixture × condition (models are nondeterministic;
   single-run rates are noise). Catch rate = caught runs / N, reported per fixture and
   aggregate. `TEMPER_EVAL_REPS` overrides for cheap local runs.
5. **Cost capture.** Run `claude -p --output-format json`, record `usage` tokens and
   wall-clock per run — the tokens column doubles as the data that decides the
   deferred reference-diet question (see cut list).
6. **`evals/run-benchmark.sh`** orchestrates the matrix (fixtures × 2 conditions × N),
   writes `evals/results/benchmark-<date>.json`, and renders
   `docs/evidence/benchmark.md` from it — generated, never hand-edited.

### 3b — Fixture matrix: 3 → 12

*Size: M–L — the grind, and the credibility. Nine defect fixtures + three clean.*

Rules carried over from `evals/README.md`, now non-negotiable for every new fixture:
minimal real project; `intent.md` makes the defect *visible to the methodology*;
`SEEDED_DEFECT.md` + `expect.json` with anchor+signal keyword sets; **discriminance
proof** — the fixture must demonstrably MISS when the fix is reverted and CATCH
against the real pipeline before it counts (a fixture that passes unconditionally
tests nothing). Stacks rotate across the three already in use (node-express, fastapi,
react-ts) — zero new toolchain cost.

| # | Fixture | Class | Stack | Stage |
|---|---|---|---|---|
| 1 | `password-reset` *(exists)* | missing scenario coverage | node-express | check |
| 2 | `orders-api` *(exists)* | wrong-API logic bug (`.find` on a Python list) | fastapi | review |
| 3 | `notifications` *(exists)* | implemented-but-unwired component | react-ts | review |
| 4 | silent error swallowing | `except: pass` / empty `catch` on a documented failure path | fastapi | review |
| 5 | hardcoded secret | credential committed in source, intent requires env config | node-express | review |
| 6 | boundary off-by-one | `>` vs `>=` against a limit named in intent.md | node-express | review |
| 7 | unawaited async | missing `await` → race on a documented ordering guarantee | react-ts | review |
| 8 | behavioral regression | change breaks an *existing* documented behavior the tests don't pin | fastapi | check |
| 9 | spec misread | code implements the inverse of a stated criterion (allow-list as deny-list) | node-express | check |
| 10 | clean-express | no defect | node-express | review |
| 11 | clean-fastapi | no defect | fastapi | check |
| 12 | clean-react | no defect | react-ts | review |

Class selection logic: 4–7 are defect types *reviews* are supposed to catch (tests
`gate_review`'s severity path); 8–9 are defect types only *scenario tracing* catches
(tests `gate_check`'s coverage path); 10–12 exist solely to make the false-positive
column real. This deliberately doubles coverage of both gate paths tier 1 branches on.

### 3c — Run, publish, and the honesty rules

*Size: S plus token budget.*

- **Scale:** 12 fixtures × 2 conditions × 5 reps = 120 headless runs per full
  benchmark. This is a `workflow_dispatch` + on-release job in
  `.github/workflows/eval-fixtures.yml`'s family — never per-PR. The existing nightly
  keeps running the 3-fixture regression subset unchanged.
- **Published artifact:** `docs/evidence/benchmark.md` (auto-generated) with: pinned
  model ID, plugin commit, harness commit, date, N; per-fixture and aggregate
  defect-catch rate per condition; FP rate on clean fixtures; median tokens and
  wall-clock per condition; a one-paragraph methodology section linking every
  mechanical rule above; reproduce-it-yourself commands (the harness already supports
  this via `TEMPER_PLUGIN_DIR` — bare mode makes it two commands total). README gets
  the aggregate table excerpt and a link, replacing adjective-based claims.
- **Honesty rules (in the doc, enforced by review):** publish MISSED and FP results
  unedited; no fixture or keyword edit after a published run without re-running the
  full matrix and bumping the benchmark date; the LM-judge's transcripts ship with the
  results; a regression found by the benchmark is a bug to fix, never a fixture to
  soften — the same rule `evals/README.md` already lives by.

### Item 3 acceptance

- [ ] `TEMPER_EVAL_CONDITION=bare bash evals/run-fixture.sh orders-api` completes and
      scores transcript-only, with the temper run of the same fixture still requiring
      tier 1.
- [ ] All 9 defect fixtures pass the discriminance proof (MISS on revert, CATCH live);
