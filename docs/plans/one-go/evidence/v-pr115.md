## 3. Three options

Facts that decide it:

- The four parts the restructuring will build on are all in this PR: the one runner `run_env.run_cmd`
  (`scripts/run_env.py:183-205`), the setup block (`:76-118`), the policy (`scripts/flow.py:1144-1181, 1963-1972,
  2457-2472`) and the reuse store (`scripts/run_env.py:121-180`). The runner and the setup block are sound. The policy
  needs M3 to M6. The reuse store needs a test (U4) and a guard (M14).
- The features are not separable by commit. 10 of the 16 commits touch `scripts/flow.py` and 8 touch
  `scripts/temper`; `7859742` holds the setup block, the stored preflight, doctor and the ENV verdict together;
  `a9068b7` holds three features; `30d94ac` holds five.
- A push costs 30 minutes of CI when green and 60 when an e2e scenario loops (`pr-tests-ci.md`, section 1).
- There is one open PR and no other work on main, so nothing waits on a smaller first merge.

| | (a) Fix on the branch, merge as 9.8.5 | (b) Split the PR | (c) Leave it open, take from it |
|---|---|---|---|
| Work | 16 small fixes, 4 flips, about 20 selftest cases, 1 or 2 e2e scenarios, one fixture regeneration | The same fixes, plus re-cutting 16 commits into about 4 PRs by feature: (1) runner, setup block, plain doctor, failure text, the four option cap, reuse, lock, `evidence run`, Maven rows; (2) the policy; (3) preflight, propose, ENV and SETUP verdicts; (4) the changed defaults and plan patch | The restructuring copies the runner, the setup block, the policy and the reuse store by hand, with their tests (case files 21 to 31) |

| Risk | The PR grows a little more before it lands | Each cut needs its own fixture regeneration and its own e2e pass; intermediate states are new, untested combinations | Main stays at 9.8.4 without the runner; the branch drifts; the three bugs the replay found stay unfixed on main; the fixes found here are lost unless redone |
| What the restructuring starts from | Main with all four parts, tested, defaults quiet | The same, later | Main without them |

**Recommendation: (a).** The defects are local and small, the parts worth keeping are exactly the ones the
restructuring needs, and the commits do not split along features, so (b) pays several CI cycles and a re-cut for no
gain and (c) makes the restructuring re-land the same code. Hold (a) to a strict scope:

1. Settle section 4 and F1 to F4 first (they decide what M4, M5 and the fixtures look like).

## 4. The owner decision: "an unattended run never plans again"

**What the code does under `autonomy.policy: decide`** (ran: `exp1`, `exp6` on the head):

1. A group check fails in an armed run. The policy takes the question's recommended option by itself
   (`scripts/flow.py:1963-1972`): `group fix G1`.
2. The fix agent is not launched, because the launch needs `not r.armed()` (`scripts/flow.py:1754`). The next step
   sees `fix_tries` 1, so the recommended option is `Loop back to Plan` (`:2003-2005`), and the policy takes it:
   `state loop build plan --reason 'policy: group G1 failed its check (...)'`.
3. The CLI archives the grouped run ("grouped run reset for the re-plan", `scripts/temper:1276-1279`), spends the one
   Build to Plan step (`scripts/loop_step.py:24-25`) and launches the Plan agent on Opus. No park, no report, no
   question before it.
4. The new plan is put to the person: Plan is never an armed move (`scripts/flow.py:2441`). But the run is still
   armed whatever they answer (M5).

With M3 fixed, step 2 launches the fix agent first; a fix that does not pass still ends in the same unattended loop
back to Plan.

**What the documents say.**

| Document | Says |
|---|---|
| `templates/temper.config.default:138-141` | "Hardcoded, not configurable (safety invariants, not preferences): autonomy ... NEVER re-plans unattended." |
| `reference/autonomy.md:28` | "Build never loops back to Plan by itself." |
| `reference/autonomy.md:35` | "It never pushes, never merges to a remote, never plans again by itself" |
| `docs/grouped-build.md:123-125` | "it never pushes, never merges to a remote, never re-plans" |
| `docs/decisions/0011-*.md:88-89` | "It still never pushes, never merges to a remote, never re-plans" |
| `docs/flow.md:231-233` (new in the PR) | The policy takes the recommended option by itself: "a fix agent, a longer limit, the tasks again, a loop back to Plan" |

Four documents say never; the PR's own page and the code say it does.

**The two ways to settle it.**

| | Way A: keep the rule | Way B: change the rule |
|---|---|---|
| Rule | An unattended run never sends itself back to Plan. At that recommendation it parks and the person is asked. | An unattended run may send the plan back once; no new plan is built on without the person's approval. |
| Code | One condition at `scripts/flow.py:1968` (M4), plus M3 and M5 | M3 and M5, a park report so the person knows why they are at Plan again, and nothing else |
| Documents | One sentence in `docs/flow.md:231-233` | The four texts above, `.claude/CLAUDE.md`, and an amendment to ADR 0011 |
| Cost at run time | A park and one question | A whole Build thrown away and a Plan pass on Opus (143 to 246 s and $0.75 to $1.13 on the benchmark, 12 minutes on the measured Java run) before the person sees anything |
| Test | `temper-cases-28.sh`: the policy parks, never `state loop build plan` | `temper-cases-28.sh`: one loop, then interactive; a second failure parks |

**I recommend way A.** It is the smaller change, it keeps four documents true, and a loop back to Plan is the most
expensive move a run has: it discards every task's work. That is a decision for the person, and the restructuring
aims to repair in place instead.

## 5. What this PR does for a default user who changes no config
