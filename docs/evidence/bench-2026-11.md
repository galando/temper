# Evidence: Temper against vanilla Claude Code and a careful prompt (2026-11)

The harness is `bench` (its README says how to run it). Every arm got the same task text, word for word, the
same model (Claude Code's default, Opus 5.5, with Temper's own agents on Sonnet and Haiku where it chooses), no user or
project settings, and the same simulated person, who approves, fixes rather than skips and never overrides a gate.
Three repetitions per task per arm; 63 runs in all, $83.85 of model use at API prices.

| Arm | What ran |
|---|---|
| vanilla | the task as the prompt |
| careful | the task, plus: read the code and plan, write failing tests first, run the suite, wire it in, add nothing extra |
| temper | `/temper:temper <task>` for a feature, `/temper:fix <task>` for a bug |

## The tasks

| Task | Kind | What makes it hard |
|---|---|---|
| slugify | small feature | nothing: a pilot task |
| login-lockout | medium feature | the change must be wired into the app |
| orders-pagination | medium feature | edge cases: ties, tampered cursors, inserts between pages |
| partial-payments | large feature | statuses, refunds per payment, void and credit note rules, export columns, every house rule |
| subscriptions | large feature | month end anchoring, leap years, catch up billing, tenant timezone, half to even proration |
| cent-mismatch | bug | the ticket names two places; the cause is in three; "fixing" the app to match the export breaks a house rule |
| tenant-leak | bug | a read cache keyed without the tenant: it leaks reads, export names and write decisions |

The last four live in Ledger, a ~560 line multi-tenant invoicing service with house rules in `CONVENTIONS.md`.
Every hidden assertion follows from the task text or a house rule. Each task's reference solution passes its hidden
tests and the untouched code fails them.

## What it shows

1. **Correctness: parity.** Every arm passed every hidden test in every run, on every task. On these tasks, with this
   model, Temper does not produce more correct code. The tasks did not separate the arms; harder ones are needed to
   find out whether a gap exists.
2. **The tests left behind: Temper is ahead, unevenly.** Its suites caught more planted bugs: 94% against 89% and
   88% on the hard tasks. The gap is large on subscriptions (96% against 85% and 77%) and the pilot tasks, and
   none on partial-payments and the bug tasks. On a bug, every arm wrote a test that catches the bug if it returns.
3. **Cost: about 10 times more, and 11 to 13 times slower.** $3.65 and about 15 minutes per hard task against
   $0.37 and about 1 minute. The bug flow is the leanest part (`/temper:fix`: $1.58 to $2.91, 5 to 8 minutes).
4. **Scope: Temper writes files nobody asked for.** In 11 of 21 runs it added an ADR under `docs/decisions/`, and in
   two runs it left its own run state files (`gates.json`, `status.json`, `view.json`) in a `.temper/` folder inside
   `docs/decisions/` or the spec folder.

## Temper defects the runs found

- **A failed gate with no way out.** When the Intent agent asked for a reviewer's name and none was given, the
  Intent gate offered only Override, Grill Me and Save for later. Grill Me ran ten rounds and returned to the same
  failed gate: 25 questions and $6.61, no code. Only one run of 21 asked for a reviewer at all.
- **Coverage recorded as none.** Check failed once with "recorded coverage 'none'" although coverage was installed,
  and passed when run again.
- **Run state written outside `.temper/`** (above).
- **ADRs by default**, which a task never asked for (above).
- **Cost varies widely** on the same task: tenant-leak cost $1.66, $5.35 and $1.72 across three runs.

## Limits

- The tasks were written by the Temper author, though every hidden test was checked against the task text and the
  house rules, and against a reference solution. A claim to the world needs tasks from outside.
- Three runs per task per arm, one model, Python only, codebases under 1,000 lines.
- The simulated person approves everything Temper proposes. A real person at Temper's questions brings knowledge the
  benchmark cannot: the questions Temper asked (a credit note's effect on the balance, for one) are a value these
  numbers do not count.
- Equivalent mutants (ones no test could catch) lower every score alike; the score is a comparison, not an absolute.

## Round 2: vague tasks (27 runs)

Temper's claim is that it pulls out what the person knows before code is written. Round 1 gave every arm a complete
spec, so that claim could not show. Round 2 gives a vague ticket that names the endpoint and leaves the rules out.
Each task has a private brief (5 or 6 numbered facts) that a product owner model (`person_llm.mjs`, Sonnet) uses to
answer any question, in every arm: only what is asked, every fact that answers a broad question, nothing it does not
know. It logs which facts each answer revealed. When a session ends with a message that waits for an answer, the
owner answers it. Hidden tests split into ticket tests and one group per brief fact.

| Task | The ticket | The brief |
|---|---|---|
| vague-refunds | refund paid invoices; the endpoint | admin only; a 60 day window; partial refunds with a cap; a reason required; a `refunded` status |
| vague-late-fees | a daily late fee job; the endpoint | the fee invoice's line; 2% with a 5.00 minimum; a 7 day grace period; once ever; small invoices exempt; no fee on a fee |
| vague-discounts | discounts; the endpoint and fields | draft only; before tax, line by line; 20% for a clerk, 40% for an admin; replace and remove; an export column |

The arms: `vanilla` (the ticket), `careful-ask` (the careful words plus "If the request leaves something important
unclear, ask me before you build it"), `temper`.

| Arm | Ticket tests | Brief facts met | Facts learned before building | Runs that asked before building | Cost per run | Time per run |
|---|---|---|---|---|---|---|
| vanilla | 42/42 | 35/48 (73%) | 0/48 (0%) | 0/9 | $1.04 | 106 s |
| careful-ask | 42/42 | 41/48 (85%) | 26/48 (54%) | 7/9 | $0.87 | 119 s |
| temper | 42/42 | 40/48 (83%) | 28/48 (58%) | 9/9 | $7.69 | 981 s |

Per task, brief facts met: discounts 93% / 93% / 100%; late fees 61% / 94% / 89%; refunds 67% / 67% / 60%
(vanilla / careful-ask / temper).

### What round 2 shows

1. **Asking first matters.** The arms that ask before building meet more of what the person wanted: 85% and 83%
   against 73%. Vanilla never asked before building in any run; every fact it learned came from questions in its
   closing summary, after the code was written.
2. **Temper asks every time; one sentence of prompt does as well.** Temper asked before building in 9 of 9 runs,
   careful-ask in 7 of 9, with the same outcome (83% and 85%). Temper costs about 9 times more and takes about 8 times
   longer.
3. **Temper's questions are narrow.** On refunds it asked about partial refunds and the status in all three runs and
   never about who may refund or a time limit; it assumed the house rule that clerks change data. A vanilla run that
   asked one broad question ("any rules I should know?") learned all five facts.

### Temper defects found in round 2

- **One move name for two decisions.** `accept` means both "accept a review finding" and "accept a task an earlier
  task already built". When a later Build task's tests passed before any code, the question looped on "Run it again"
  and the code stayed in a task worktree. (The benchmark's person refused `accept`; it now takes the covered task, and
  the two affected runs were rerun. They cost $25.33 and $23.23 and are not in the tables.)
- **Expensive follow ups.** After a run, answering one question cost Temper several Opus turns over its large
  context: one discounts run cost $16.68.

Round 2 spend: $87.61 in the tables, plus $48.56 for the two invalid runs.

## Round 3: Temper 9.8.0 (33 runs, then 6 reruns after the loop fixes)

The same 10 Ledger tasks and a TypeScript task (seat holds), 3 runs each, against the earlier arms. Temper 9.7.6 is
the version of rounds 1 and 2. Spend: $181.29 for the round (the Temper runs and the TypeScript baselines), $19.78 for
the reruns.

| Arm | Runs | All hidden pass | Brief facts met (vague tasks) | Outside scope | Mutation score | Median cost | Mean cost | Mean wall |
|---|---|---|---|---|---|---|---|---|
| vanilla | 33 | 27/33 | 35/48 (73%) | 1/33 | 79% | $0.36 | $0.51 | 70 s |
| careful-ask (vague tasks only) | 9 | 4/9 | 41/48 (85%) | 0/9 | n/a | $0.92 | $0.87 | 119 s |
| temper 9.7.6 | 30 | 25/30 | 40/48 (83%) | 13/30 | 94% | $3.69 | $4.66 | 847 s |
| temper 9.8.0 | 33 | 31/33 | 47/48 (98%) | 1/33 | 93% | $2.56 | $5.43 | 856 s |

### What round 3 shows

1. **9.8.0 meets what the person wanted.** On the vague tasks it met 98% of the facts the hidden tests check (all of
   them on refunds, where 9.7.6 met 60% and careful-ask 67%), because Intent works through a rules checklist and the
   person clicks answers.
2. **It stays in scope.** Files changed outside the plan fell from 13 of 30 runs to 1 of 33 (the scope row is now in
   every run, and the person adds a file to the plan or not).
3. **A typical run is cheaper than 9.7.6, the mean is not.** The median fell 31% ($3.69 to $2.56). Three runs ($38.24,
   $26.91, $23.19) looped at Check on a locked acceptance test (below); without them the mean is about $3.
4. **It is still far dearer than vanilla:** about 7 times the median cost and 12 times the time. On a task the request
   specifies fully, vanilla reaches the same correctness; Temper's gain there is stronger tests (93% against 79%).

### The loop at Check, and the reruns

In three runs a locked acceptance test failed at Check. Build's fix pass got only the name of the failed run, found
nothing to change, and Check failed again; one builder then edited the locked test, after which Check failed on
"changed after they were locked" until the person was asked to override. One test was wrong (it assumed customer ids
are global, where this code base numbers them per tenant), one had a wrong helper, one a wrong fixture sum. The fixes:
the step back carries the failing output, the person can correct a wrong test ("Correct the acceptance test", with a
reason the report keeps), a lock is taken once and keeps a copy, and "Restore the locked tests" puts back an edited one.

| Task | Before: hidden, cost | After the fixes: hidden, cost |
|---|---|---|
| vague-late-fees | 13, 12, 13 of 13; $26.91, $3.88, $23.19 (mean $18.00) | 13, 13, 12 of 13; $2.99, $4.13, $2.77 (mean $3.30) |
| subscriptions | 23, 25, 25 of 25; $3.46, $3.81, $38.24 (mean $15.17) | 25, 24, 24 of 25; $5.98, $3.90, $5.17 (mean $5.02) |

Two reruns met the failing acceptance test again; both took "Correct the acceptance test" after one step back to Build,
and both corrections were right (a helper that read the list answer wrongly, a date case), with the hidden tests
passing on what they checked. No run looped.

### What 9.8.0 still misses

- **A case no test covers.** One subscriptions rerun answered 404 for a canceled subscription (the task says it stays
  readable as `canceled`). The acceptance tests never read a canceled one, so neither Review nor the mutation score
  could see it.
- **An exemption folded into another question.** Two late-fees runs never asked whether small invoices are exempt;
  Intent asked "Which invoices count as overdue?" and the answer covered only the due date.
- **A house rule offered second.** One subscriptions run listed "No tax" first for the invoice tax, against the house
  rule that taxes every line; the benchmark's person takes the first option. Intent's brief says to recommend the house
  rule; the model did not.
- **One wasted round.** When the code was right and the test wrong, the step back to Build first failed its RED then
  GREEN row (nothing to change) and ran again before the person was asked to correct the test.

### What round 5 shows

1. **A guarded Haiku loop costs $0.03 to $0.09 a run**, against $0.27 to $0.85 for the Sonnet loop, and its context
   stays under Haiku's 100,000 token price step (all but 9 of its 288 turns). With the request checks (item 5) it lost
   no hidden test, no fact of the brief and no file of scope on any of the four tasks, and it took about as many turns
   as the Sonnet loop (49 against 62 on vague-refunds; round 4's unguarded Haiku loop took 80 and 84).
2. **The whole run is about $0.30 cheaper on a bug (about 30%), $0.63 on vague-refunds (23%) and $0.93 on
   partial-payments with the request checks (27%)**, by the means of each arm. It is not a dramatic cut, because the agents did not change.
3. **The Sonnet loop on round 5 code is not much cheaper.** The bug runs fell by about $0.05 to $0.10 and
   partial-payments by about $0.50; each round 5 Sonnet vague-refunds run took a second Review round (a finding fixed,
   then reviewed again), $0.40 to $0.50 more. Fewer turns and less context matter little at Sonnet's price for a
   session this short.
4. **Opus is now two thirds to four fifths of a run on the Haiku loop** (64% to 83%; vague-refunds: Plan $0.95 and
   Design $0.49 of $2.00). The
   next cut has to come from the Opus agents, and from work an agent does that the CLI can do.
5. **The Haiku loop failed partial-payments twice the same way** (14/26): it started the run with

   With both, the Haiku loop met all 26 hidden tests in both runs ($2.69 and $2.41, against $3.37 and $3.59 before
   round 5). In both runs the session again passed a summary to `state init`, was refused, and passed the request
   whole; in one, the plan left out `GET /invoices/{id}` and the row sent Plan back to name it.
6. **One more defect, in the CLI:** a request that ended with a period got a second one in the Intent agent's prompt;
   the Haiku session tidied it to one, and the guard refused the launch as another prompt (both runs, one turn each).
   The prompt now carries one period.

### Defects the A/B found in round 5's own changes (fixed before the counted runs)

Ten runs in two earlier passes (`v1`, `v2`) are not counted: each pass was stopped when the guard refused a step the
CLI had given.

- The mod's memory of the agents it may launch did not survive the engine loading the mod again between turns: a
  task's `task start` turned the next action into `wait`, and the agent it had named was refused. The view now names
  every agent named at the run's stage.
- Two view writers resolved models differently (`group start` wrote "Model: haiku." where `next` wrote the model id),
  and the launch was refused. One path writes every view.
- A fix pass prompt held a raw traceback that the Haiku session copied wrong; its launch was refused. Findings in a
  prompt are now short.
- The same reload would have lost the skill the person chose (Grill Me, Teach Me), whose questions the guard lets
  through; it is now in the plugin store.
- The e2e driver found two more: one action that names two task agents at once, and a manual task's question after
  its task start.

Set aside for the harness, not for Temper: runs where moving `bench/node_modules` aside left the SDK's native binary
unresolvable (`invalid/*-sdk-path`, `*-sdk-copy`, `*-module-moved`), and one Haiku run on a view bug fixed before the
counted runs (`invalid/haiku-vague-refunds__temper__2-old-view-bug`).
